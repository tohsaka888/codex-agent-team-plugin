# Matt 工作流指引

先完成 preflight.md 的适用必需项检查。本文是跨项目的流程适配说明，不替代 Matt 上游 SKILL.md；实际选用时读取正文及引用，遵守用户主动调用边界和项目规则。

1. 澄清与探索：恢复用户目标、项目领域和已有方案；需要时使用 grill-with-docs、domain-modeling 或 research。识别当前阶段，已确认范围的小修复或文案修改说明沿用依据，不重复制造全套规格。
2. 验证边界与规格：新功能使用 to-spec，先提出实际验证边界并按技能要求与用户确认，再形成可查看的规格。关键架构取舍或视觉方向确有需要时另给 ADR/原型；提交具体版本等待相应确认。团队启用、检查通过、Agent 同意、用户沉默均不代替确认。
3. 工单拆分与确认：使用 to-tickets，形成可独立验证的纵向切片，列明输入、产物、验收、阻塞依赖及本地/外部 tracker 位置。按技能要求确认粒度和方案，恢复已有明确确认时不重复询问。
4. 实施：依据已确认规格和工单，通过 implement-spec 的适用流程推进任务依赖；行为修改按 tdd，难复现缺陷按 diagnosing-bugs。按原生团队能力分派，写入隔离、权限及提交行为遵守当前项目和用户授权。与上游 Git/worktree 条件不同的执行方式明确记录适配依据。
5. 测试与审查：运行覆盖实际风险的项目检查；使用 code-review 核对实际变更、规格和规范，修正真实发现并复查。无可用固定差异时记录限定文件审查的范围和限制，不称完整上游技能已执行。
6. 交付：列出真实文件、实际技能应用、验证输出、审查结果、未完成项及限制。执行完成、Agent Review、人工规格确认和人工交付验收分别记录，不自动勾选用户验收或发布。

环境就绪解决“能否执行”，规格/工单确认解决“执行什么”；两者分别核对。恢复任务时读取对应产物和明确确认依据。任务变化导致技能、工具或执行方式变化时，先重新检查受影响依赖，再继续对应阶段。

包含 UI 的需求按 [UE 工作流](ue-workflow.md)补充图、人工视觉确认、归档和 design.md。规格/工单可先确认设计依赖，正式 UI 实施必须等待对应基线就绪；独立后端任务不追加无关阻塞。记录阶段的实际产物与确认，不以“已读技能”代表完成阶段，也不以规格确认代表全部预设角色都已派生。

如果必需 Matt 技能缺失，暂停依赖该技能的正式团队工作并按 preflight.md 补齐。不能因为能派生子 Agent 或能打开看板，就声称已按 Matt 工作流运行。
