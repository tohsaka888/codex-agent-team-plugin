# 第一阶段：本机原生 Agent Team

## 已确定范围

用户要求先实现 Agent 层：子 Agent 预设、Skills 装载、原生团队协作。验收入口已确认是本机原生 Codex 对话。
UI 仅查看，留到后续阶段；SSH、持久任务数据库、严格审批门槛及关闭 App 后继续执行不属于阶段一。
阶段一不重做插件可行性 POC，使用真实小任务验证交付行为。

## 第一步：形成可执行规格

使用 Matt `to-spec` 将已有讨论整理为角色职责、输入输出、Skills 规则、任务协作与验收条件。规格见 native-agent-team（本机记录：`../.scratch/native-agent-team/spec.md`）。
用户已确认外部验收边界：隔离小任务 → 原生角色派生 → 按需读取 Skill → 任务产物 → 协调者汇总；并行与审查反馈逐步加入。
规格已生成；推荐角色、模型配置和切片仍需通过后续任务验证，不把文档写成实现结果。

## 推荐角色与 Skills 矩阵

| 角色 | 输入 → 输出 | 按任务选择的 Matt Skills |
| --- | --- | --- |
| coordinator | 用户目标、规格和任务 → 分派、汇总与返工安排 | to-spec、to-tickets、implement-spec |
| requirements | 已有需求与边界 → 用户故事和验收条件 | domain-modeling；需要澄清时 grill-with-docs |
| architect | 规格和代码 → 方案、模块边界和必要 ADR | codebase-design、domain-modeling；有具体不确定性时 prototype |
| developer | 有界工单 → 实际变更和验证结果 | tdd；缺陷诊断时 diagnosing-bugs |
| reviewer | 规格、实际变更及测试 → 问题、依据和复查结果 | code-review |

五份可选角色预设已创建，使用约定见 [团队合同](native-team.md)。角色职责由原生委派表达，Skills 由 Codex 发现并由 Agent 按需使用；自定义角色自动装载不是必需验收。原生本机配置与协作交付已有实证，核对见 [设计对齐](research/native-design-alignment.md)。测试职责先由 developer 的验证和 reviewer 的独立检查覆盖；只有任务确有需要再增加独立 tester。
本版模型与推理强度继承父会话；覆盖配置仅在用户授权及宿主实际支持时另行核验，不擅自改变登录、供应商、权限或预算。模型使用权与权限以宿主实际策略为准。

## Skills 装载的四个层次

1. 安装：项目中有固定版本的完整 Skill 文件。
2. 发现：当前 Codex 和派生角色能看到所需技能的目录信息。
3. 读取：执行具体任务时读取对应 SKILL.md 与必要引用，按需装载。
4. 执行：按该技能步骤产出结果与证据；保留用户主动调用的边界。

角色矩阵是任务选择建议，不是插件技能装载器或安全 allowlist，也不意味着把 31 个技能全文预加载到每个上下文。需要限制启用范围时使用当前版本支持的原生配置并实际核验。
`disable-model-invocation` 的原文保持不变；协调者记录当前用户授权的流程范围，不能靠删除标记让所有子 Agent 自主运行用户专属技能。
配置格式以 [Subagents](https://learn.chatgpt.com/docs/agent-configuration/subagents) 与 [Build skills](https://learn.chatgpt.com/docs/build-skills) 为依据；本地/个人配置与角色继承实际验证后才记录为通过。

## Matt 流程与推荐切片

| 顺序 | 可独立验收的交付 | 阻塞关系 |
| --- | --- | --- |
| 1 | 预设一个角色，原生对话派生该角色，读取指定 Skill 并返回真实有界任务结果 | 无 |
| 2 | 扩展推荐角色，使协调者能为不同任务选中角色和相应 Skill | 1 |
| 3 | 两个原生子 Agent 并行完成独立工作，协调者收集并整合结果 | 2 |
| 4 | reviewer 发现实际问题，developer 修正，同一交付经复查后汇总 | 2 |
| 5 | 一个小型工程任务贯通需求、架构、分派、实现、测试、审查和交付 | 3、4 |

2026-10-02 用户已确认上述五项切片、依赖与单写入者方式，正式工单见 `.scratch/native-agent-team/issues/`。按实际依赖推进，补充实验不替代正式工单验收。
`implement-spec` 的并行写入 worktree 与合并步骤适用于已有基线提交的仓库；当前尚无首次提交，不能假装执行过这些 Git 步骤。先解决真实基线条件，或明确采用经授权的单写入者模式。
行为逻辑适用时采用 tdd；纯指令/配置修改用格式检查、装载检查和实际任务验证，避免测试只重复配置文本。
`code-review` 要求可解析且有差异的固定基线；没有该基线时先确认审查对象，不报告完整上游工作流已完成。

## 第一阶段完成标准

- 原生子 Agent 实际派生，收到明确职责并完成有界任务；可选角色配置的自动应用不作为必需条件。
- 每个实际参与角色有明确职责、写入范围和输入输出。
- 所需 Skills 的发现、正文读取与流程执行分别有证据。
- 至少一次真实并行；证据区分原生父子关系与独立历史探针。
- 至少一次实际审查反馈与修正复查；执行结束不代替验收。
- 协调者交付实际文件、运行过的验证、审查结论与已知限制。
- 本机闭环不依赖 UI 控制、SSH 登录改动或独立执行器。
