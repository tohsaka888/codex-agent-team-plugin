# 本机原生团队使用约定

当前入口（2026-10-02）：用户提及 `@Agent Team` 在当前主会话启用原生团队技能；后续需求沿用，直到退出。只读 Kanban / Org Chart 按真实主会话及其全部已观察子 Agent 展示，Workspace 作为项目筛选上下文。插件 ID 为 `agent-team`；只读工具名保留兼容。入口已打包，宿主新会话的自动匹配仍须区分于代码检查通过。
本页统一团队分派与结果字段；范围和验收以已确认规格及工单为准。团队运行属于 Codex 原生工作流，插件仅展示真实任务与执行信息。

## 原生执行与角色职责

用户在原生对话提出目标并授权团队协作，由主 Agent 协调。Codex 原生工具派生子 Agent、传递任务、等待结果及组织后续反馈。
2026-10-02 用户已明确授权本项目后续已确认工单都通过该团队流程推进，并以实际 UI 观察验证协同；这份授权适用于该工程交付，不扩展为外部消息、发布或新产品范围的授权。
按目标分配需求、架构、开发或审查职责，使用当前可用的原生委派指令即可。自定义角色 TOML 是可选定制，用于宿主支持的指令或执行配置覆盖，不是团队协作必经路径。
项目五份角色预设可保留为职责参考；本版继承当前模型和权限，没有依赖其自动配置覆盖。实际任务名不等于配置角色名。
2026-10-03 新增 UE 预设职责及可选 `.codex/agents/ue.toml`。涉及 UI 新设计或实质修改时读取[UE 工作流](../plugins/agent-team/skills/agent-team/references/ue-workflow.md)，先收集/生成图并取得具体版本确认，再归档图、UX 说明和 design.md；开发与审查引用同一基线，独立后端任务按真实依赖推进。
团队职责必须在委派合同和实际 team-sync run 中明确；优先选择可用预定义 Profile，原生工具支持对应 agent_type 时显式选择，否则使用实际支持类型并单独回报职责。已有 Profile 无法满足时允许动态职责并使用相同同步入口。规格/工单确认通过不表示已按预设职责分派，读角色文件不表示按名派生成功。不要从 api_implementation 等名字推断 Developer。
展示回报明确区分职责 role、派生 task_name 和 Hook 原生 agent_type；任务分派后将确实使用的 task_name 回报为 agentName，并关联真实 UUID。缺失历史名称、模型或权限配置不猜测。Org 汇总同一组织分支的职责，原生列表仍展示每个执行实例，两者不要求节点数量相等。
当前工具缺少自定义角色选择字段，不阻塞原生委派和 Skills 使用，不将这一接口差异设置为阶段一门槛。

## Skills 的原生发现与按需使用

Codex 从有效的系统、用户、项目与插件技能位置提供可用技能。先提供名称、描述和路径等元数据；Agent 根据任务选用后读取 SKILL.md，引用和脚本再按需要访问。
子 Agent 未设置覆盖时继承父会话的 Skills 配置；其工作目录、可用工具和用户调用限制仍影响实际使用。
“自动”指发现及按任务选择，不能理解成派生后一次加载全部技能、保证每次匹配都正确，或自动运行所有工作流。
内置角色、原生工具与系统 Skill 是不同概念；使用宿主实际提供的能力，不按内置角色名推断技能清单。
需求涉及领域模型变化时按需使用 domain-modeling；架构使用 codebase-design；开发按任务使用 tdd 或 diagnosing-bugs。仅消费已有术语时读取 GLOSSARY.md。
用户专属技能保留其调用边界；不为实现自动技能选择删除上游标记，也不由 UI 插件进行技能注入或调度。

## 分派合同

每次委派明确 Task、协调者分配的 AgentRun、职责、目标、输入、产物、写入范围、验收条件与依赖。
分派前协调者读取 [team-sync](../plugins/agent-team/skills/team-sync/SKILL.md)，登记 team 和尚无执行的 task；成功分派及目标变更后保存关联 run、目标和真实宿主身份。委派提供实际 Skill/脚本路径、workspace/data-dir、team-id/task-id/run-id，要求成员读取并查询核对。自然语言回复无需 JSON；旧 report-goal/task-report 保留历史兼容。合同及独立 Web 边界见 [可移植追踪](portable-tracking.md)。
按任务提供必要上下文与可用技能指针；子 Agent 自主选择适用的方法，读取所需正文并返回具体应用结果。是否读角色参考由任务需要决定。
当前采用用户确认的单写入者方式：子 Agent 只读分析及运行不会改动项目的检查，协调者落盘。这是协作约定，不替代宿主权限控制。

## 结果与协调

结果记录 Task、AgentRun、真实工具身份、职责、实际使用的 Skills、产物、验证、限制及待修正项。
任务启动时回报独立的 acceptanceItems（稳定 id、label、pending），核对后逐项更新 status、evidence、reportedBy。未核对保持 pending/unknown；用户视觉验收单列，收到明确回复后再更新。
评审者返回署名、Agent/人工身份、设计/交付范围、结论、具体反馈及依据。协调者逐次回报 reviewRecords，保留初审需修正与最终复查，不用“通过”标签替代记录。人工记录引用真实用户确认，不从 Agent 结果推断。
产物回报工作区内实际文件 reference；历史任务和评审关联真实 nativeAgentId，便于查看执行会话。完整字段与增量更新语义见 [展示合同](ui-data-contract.md#验收评审与导航)。
AgentRun 为协调者分配的本地记录，与原生身份分别保存；缺失或未知信息不补造。
子 Agent 报告实际观测开始/结束时间，协调者保留工具返回身份和结果。并行以独立任务及工作时间重叠为据。
协调者按依赖整合结果、运行相关检查，安排独立审查；针对真实发现修正并复查，未发现问题如实记录。

## 限定文件审查

协调者提供本次范围及文件指纹。新文件审查完整内容，既有文件按可取得的修改前文本检查；没有基线时明确只能检查当前内容。
reviewer 对照规格和合同，检查用户调用边界、引用、产物和证据；发现包含文件依据、严重度和建议。
修正后更新指纹并复查同一问题，旧审查结果不代表新版本通过。没有用户指定且对当前交付有效的固定审查基线时，使用限定文件审查，不声称完整上游 code-review 已执行。当前 Git HEAD 可解析，但不能把其他协作者的历史差异归入本轮交付。
