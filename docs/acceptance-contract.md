# 强制验收合同 v1（待用户确认）

日期：2026-10-04。依据：用户要求每张任务卡必须有 AC，Agent 自主验证，人工必须验收结果；Developer 编码变更必须有单元测试，UE 必须有用户确认原型。本文件为待实施规格，不代表现有实现已满足。

## 范围与边界

覆盖业务父工单、独立执行卡及协调者直接承担的任务。角色预设和动态角色使用相同合同。原生执行状态、Agent 验证、Agent Review、人工结果验收独立记录。

继续使用原生执行、可移植同步和只读 UI。在同步写入及协调者分派/交付流程落实必需条件；UI 展示缺失和未验收，不增加批准按钮，不拦截宿主原生工具。人工通过原生对话验收，由协调者按原话同步。

## 每张卡的 AC

1. 创建业务任务时原子提交非空 AC 集合；缺失、空数组、空白内容、重复 id 均拒绝写入。不能先创建空任务再补条件。
2. 每项有稳定 id、具体可观察条件、验证方式、责任方（Agent 或人工）、目标卡片及当前条件版本。避免“完成开发”“验证通过”等无可核对对象的空泛表述。
3. 新执行卡在分派前具有非空、有界 AC，可明确引用父工单条件，也可补充本次执行条件；保存具体引用及版本。不能默认复制父工单全部条件或自动继承父项通过状态。
4. 父工单与执行卡的结果证据分别关联；一次执行通过不自动完成父工单，父工单验收不自动认可未被确认范围覆盖的执行卡。
5. 每张卡必须包含至少一项可由 Agent 自主核对的条件，以及人工对本卡结果的验收条件。人工项不可由 Agent 标记通过。协调者、Reviewer、探索和只读任务同样适用。

## 角色必需条件

| 角色或任务类别 | 必需的具体 AC |
| --- | --- |
| Developer 编码变更（包括缺陷修复） | 覆盖实际行为/回归风险的单元测试实际通过，记录命令、结果和测试文件；集成、构建、lint 仅补充，不能替代单元测试；人工验收实际变更和验证结果 |
| Developer 纯文档/配置工作 | 核对实际引用、格式、配置合法性及相关风险，记录具体结果；人工验收产物。明确分类依据，不将编码任务改名规避单元测试 |
| UE | 原型可查看且覆盖本次范围；用户明确确认具体版本原型；确认后的图、UX 说明和 design.md 基线一致，规范校验实际通过；人工验收 UE 交付。原型确认和最终结果验收分别记录 |
| Requirements | 需求边界、用户故事与可观察 AC 完整且可追溯；Agent 核对冲突、遗漏与依赖；用户确认需求产物 |
| Architect | 对照需求核对方案、模块边界、风险及取舍；存在关键决策时提交 ADR 并取得用户确认；人工验收架构产物 |
| Reviewer | 对照当前 AC、实际版本、产物和验证证据完成审查，问题有文件/位置依据，修正后复查；人工验收审查结果 |
| Coordinator / 动态职责 | 明确本次结果和核对方法，检查依赖、证据及确认范围；人工验收本卡结果 |

角色模板提供最低要求，协调者必须结合具体任务补充业务 AC。无法运行必需单元测试时记录失败/待补和原因，保持未满足；不以“不适用”跳过编码任务测试。没有关键架构取舍时不制造 ADR。

## Agent 验证与人工验收

- Agent 执行后逐项核对其负责的 AC，记录结果、实际证据、验证者、时间、产物版本/指纹及 task/run 标识。未运行保持 pending/unknown；失败保持 failed，安排返工。
- 提交评审前，所有 Agent 可验证项必须通过并具备证据，交付产物已关联；人工项可以待确认。UE 尚未确认的原型不能放行依赖该原型的开发。
- Agent Review 按既有团队流程完成并记录，不能替代人工结果验收。人工拒绝则进入待修正；修正后重新验证受影响 AC 并提交结果。
- 人工确认需对应明确卡片、结果版本/指纹和范围，保留用户原话、时间及协调者署名。一次回复可以验收多张列明的卡片；未列明的卡片不能被自动批量认可。
- 业务完成必须满足非空 AC、全部必需项通过、适用 Agent Review 无未解决问题、当前结果已获人工验收。同步入口拒绝跳过条件直接写 completed。
- 原生 run 的 completed 只表示执行结束，即使没有 AC 也保留真实观察；展示为“执行结束 · 验收待完成”，不能投影成业务验收完成。
- AC 或结果发生实质变更，旧验证和人工认可留作历史，但不满足当前版本；不能复用旧指纹或仅凭旧通过状态完成新版。

## 历史数据和只读展示

保留旧事件读取，不改写真实历史，也不为截图任务编造条件、测试或用户确认。历史缺 AC 的卡片显示“AC 缺失 · 待补齐”，明确列出欠缺的验收信息；执行结束记录继续可查。

恢复/续派旧任务前先补齐当前版本的真实 AC；补齐后仍须实际验证及人工验收。仅观察到的原生卡暂未同步 AC 时同样显示缺失提示；插件无法阻止未经团队流程的原生派生，协调者规则要求分派前登记。

沿用现有布局、四列和 checklist。卡片展示 AC 数量、Agent 验证进度和人工验收状态；详情展示具体条件、证据和版本。未人工验收的已结束卡进入评审区域，业务“验收完成”与原生“执行结束”使用不同文案。父卡与执行卡、Kanban 与 Org 使用一致投影。

## 本次功能验收条件

- AC-01：公开 CLI 新建任务与执行卡均拒绝空 AC、空白及重复 id；拒绝后事件文件无新增，合法输入可一次创建。
- AC-02：Developer 编码任务缺少具体单元测试条件不能分派/登记执行，测试未运行或失败不能进入待评审；实际通过证据可提交评审。
- AC-03：UE 必需原型人工确认，Agent 通过、旧版本确认和部分页面确认不能放行未覆盖的 UI 开发。
- AC-04：Agent 验证和人工验收独立；Agent 不得写人工通过；未验收、人工退回、AC/产物版本变更都不能写业务 completed。
- AC-05：父工单和每张独立执行卡都有条件与自身证据；跨卡、跨 run 或旧版通过不能被错误复用；多卡明确批量验收可正确记录。
- AC-06：旧快照、缺失 AC 的原生卡和已结束 run 可继续读取，显示欠缺项，不伪造通过或人工确认；续派必须补齐。
- AC-07：真实公开同步命令→快照→Kanban/Org/详情链路与 DOM 检查覆盖以上状态；相关单元测试、lint、格式和构建通过；Reviewer 独立审查当前变更并复查问题。
- AC-08：用户对列明版本的实际交付作最终人工验收；未经确认保持待验收。

## 验证边界和实施顺序

从公开 sync CLI 写入检查到事件核心，再到同一快照的卡片/详情投影。必测负面路径包括绕过创建、空白/重复项、无测试证据、错误 run、缺人工确认、旧版确认、人工退回、更新产物后复用旧认可。测试验证行为，不以匹配 Skill 文本代替实际校验。

顺序：合同与角色规则 → 原子 AC 登记和同步校验 → 自验证/人工验收及状态投影 → UI 和迁移提示/回归/审查。沿用单写入者；现有用户修改不回退、不提交、不发布，不擅自更新远程项目或历史业务数据。

本次未引入独立审批服务或关键架构变更，不新增 ADR。沿用已确认布局，不新增视觉原型；如果实施需要实质交互/视觉变更，再单独提交具体版本。
