# 本项目人工评审流程

范围：本项目协调者约束，按已确认 Spec v1 实施。原生 Codex 管理执行与权限；只读 UI 显示回报，不阻断工具，也不提供批准按钮。

## 适用与顺序

| 触发 | 评审产物 | 确认后允许推进 |
| --- | --- | --- |
| 新功能、目标或验收条件实质变化 | Spec 与验证边界 | 确定实施范围 |
| 关键架构取舍或难以回退的决策 | ADR，包含备选方案与影响 | 依赖该决策的实施 |
| 新视觉或交互方向 | 可查看的 UI 原型 | 对应正式界面 |
| 实施批次形成或依赖实质变化 | 工单粒度、输入输出与依赖 | 对应任务分派 |
| 实施和 Agent Review 完成 | 交付文件、检查、限制 | 人工交付验收 |

Matt 顺序：澄清与探索 → 验证边界确认 → Spec/必要 ADR/必要 UI 原型评审 → 工单拆分确认 → 实施 → 测试及 Agent Review → 人工交付验收。明确列出对象后，可用一段回复确认多个对象，避免重复提问。探索和无关已确认任务可继续；等待对象的受影响实施不得分派。

已确认范围内的小修改自动执行：同时不改变目标、验收条件、关键架构、视觉方向和已确认交互。协调者在任务记录写明判断依据与回报者；需要的产物标为不适用并说明原因，不能用空数组或未回报冒充豁免。不存在必要架构取舍时不制造 ADR；文案和格式修正不强制制作原型。安装、发布与权限仍遵循原有授权。

## 每次分派前

1. 阅读 [评审索引](agents/review-index.md)、相关 Spec 和工单，恢复当前评审对象及依赖；不能依赖页面保持打开或模型记忆。
2. 为每个适用对象指定稳定 id、类型、实际文件引用、版本、SHA256、影响任务。保存被评审原文；后续状态记录与产物文本分开，避免改写批准依据。
3. 提交具体可查看的版本与确认范围。仅将用户对该明确对象的确认保存为人工决定，保留原话、上下文、对象版本和指纹。团队授权、超时、没有回复、含糊“继续”、Agent 通过及执行完成均不构成新的产物确认。
4. 核对所需对象均已确认或有依据地不适用。部分确认只满足对应对象，不放行仍依赖其他待确认对象的任务；在分派合同列出这些条件与影响任务。已有执行遭遇退回时，由协调者安排暂停依赖实施或有界返工，UI 不执行取消。

## 变更与恢复

实质变更保存新版与新指纹，旧确认留作历史并重新提交受影响对象；无关对象的确认保留。当前版本的明确人工退回覆盖此前通过，修正后重新确认。普通意见保留历史，不改变最近的明确决定。小修改无需重新提问，但保留所依据的已确认基线及变化范围，不给新指纹伪造人工确认。

跨回合或新会话仍先读索引、确认原文与文件，再核对版本、指纹、范围、依赖。找不到证据保持未知/待补，禁止把旧完成状态升级为已人工确认。恢复后按上述步骤推进；文件恢复或测试夹具通过不能声称真实新会话实测完成。

## 回报与交付

`reviewRequirements` 表达当前条件，`reviewRecords` 表达署名与依据，字段见 [展示合同](ui-data-contract.md)。两者只投影协调者声明；来源字符串不是用户身份认证。协调者核对保存的原文与 SHA256，不能仅依靠回报中的指纹证明文件没变。

任务执行完成、Agent 审查通过、人工设计确认、人工交付验收分别记录。最终交付列出实际文件、检查与审查结果、未核对事项，并保留交付验收为待用户确认。若本轮用户已经明确验收对应交付版本，再记录实际依据，不重复询问。
